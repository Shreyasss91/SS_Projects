`main.py:463-468` joins four workers one after another, each `join(timeout=_JOIN_TIMEOUT_SEC)`
where `_JOIN_TIMEOUT_SEC = 10.0` (`main.py:64`). Worst case is therefore **40 s cumulative**, not 10 s.
Order: feed -> processor -> `db_shutdown_event.set()` -> db_writer -> raw_writer. A worker that

`tests/test_integration.py:186` (`test_real_four_thread_pipeline_end_to_end`) has a deterministic

four 10 s joins. Part 2 then spawns a `--replay --catchup` subprocess (its own `timeout=120`) that
builds DuckDB, then replays it a second time in-process and verifies. A 60 s pytest cap leaves
~3.6 s of margin and cannot fit. It passes at 13.75 s in isolation.

### Resolved

**PermissionError: `INFERRED` -> `ESTABLISHED`.** Both events (`11:10:03,162`, `15:24:50,126`) fall
+4 ms and +1 ms from a watcher sample. `f10_live_monitor.py` opens the file at line 480 and stamps
`at` at line **488** (after the read), so the file is open in the ms preceding the stamp. `at` was
proven to be the watcher's own free-running clock (not quantised at 1/5/15 s), so the match is not
an artifact. P(both by chance) ~ 1 in 3.5 million.

**15-leg / 361 minutes: EXPLAINED, and it is not an allocation question.** `premium_legs` was 15 in
**all 1293** samples — the framework held the full budget 100% of the time. `delivering_legs`
(`websocket_client.py:791`) counts legs with `LegState.DELIVERING`, which per `broker_adapter.py:127`
means "at least one packet observed on this wire symbol" and is **sticky** until release/reconnect.
So it measures *liquidity across the chosen strikes*, not framework health. Only the innermost ~5 of
the 15 ATM-adjacent strikes ticked for most of the session; all 15 ticked in the final 40 min.
The 15-leg window is **13:56:29-14:36:32 = exactly the D18 window**. `actual_depth` held
`NIFTY:50` for the whole 324.6 min, so degradation hypotheses are eliminated.

seconds-to-minutes; `Grep` times out at 30 s and `Bash` calls routinely need `run_in_background`.

## Environment gotcha: deletes are blocked on this UNC share

`rm -rf` is intercepted by a trash-based safe-delete guard whose backend cannot resolve UNC paths
(`Os { code: -2147024894 }` / "system cannot find the file specified"). It hooks `shutil.rmtree`
and even `Path.unlink`, so **there is currently no way to delete files on this share from here**.
Don't burn time on it. Consequence: a stray `analysis/__pycache__` from `py_compile` cannot be
removed — but it is harmless, because the repo `.gitignore` already covers `__pycache__/` and
`*.pyc`, and the tree already carries ~140 `.pyc` files elsewhere.
